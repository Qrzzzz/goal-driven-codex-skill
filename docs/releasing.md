# Release Verification Checklist

Use this checklist for a concrete versioned release; publishing and pushing tags require the repository owner's authorization. Never replace an already published version/tag.

1. Start from a clean, current checkout. Group issue fixes by the planned version. Align `skill/VERSION`, both README version strings and smoke commands, and `CHANGELOG.md`. Record the issues addressed and distinguish deterministic tests from unperformed model-dependent evaluations.
2. Run `python -m unittest discover -s tests -v` and `python skill/scripts/check_install.py --expected-version 1.4.0` (replace with the intended version). Confirm `agents/openai.yaml` retains `policy.allow_implicit_invocation: false`. Verify all local Markdown links, including links from both READMEs, examples and references. Check changed Markdown for readability and bilingual agreement.
3. Commit and push the intended version; require successful Windows and Ubuntu deterministic CI **for that exact commit** before publishing. Inspect the final Git diff and working-tree status; do not package user-owned dirty files or local checkpoints.
4. Build the install ZIP **from the committed tree**, with the root folder `controlled-goal-driven/` containing only the contents of `skill/`. For example, from the repository root: `git archive --format=zip --prefix=controlled-goal-driven/ --output=controlled-goal-driven-1.4.0.zip HEAD:skill`. Put generated artifacts outside the checkout or remove only the known generated files before proceeding. Exclude caches and private state. GitHub's automatic source archives contain the whole project and are distinct from this install ZIP.
5. Extract the ZIP into a disposable directory and run its own `scripts/check_install.py --expected-version 1.4.0` from an unrelated working directory. Confirm the root layout, version, explicit invocation name, references and scripts; reject a stale or incomplete package. Compute SHA-256 and include a `.sha256` file naming the install ZIP.
6. Create a new annotated version tag on the verified commit, push it and publish release notes with the installation ZIP/checksum. Notes should name resolved issues, important behavior changes, actual validation evidence and material limits. Do not claim live Codex behavior/discovery verification without doing it.
7. Read the published release back. Confirm it is a public, non-draft, non-prerelease release for the intended tag, the tag resolves to the verified commit, both assets are downloadable and the downloaded ZIP matches the published checksum. Confirm addressed issues closed and that only expected issues remain. Make the latest stable version clear.

For ZIP integrity in PowerShell, use `Get-FileHash -Algorithm SHA256 -LiteralPath <zip-path>` and compare its hash to the `.sha256` text. On Unix-like systems use the available `sha256sum -c <checksum-file>` or `shasum -a 256 <zip-path>` and compare. These checks require no paid services or mandatory package manager.
